# 写真一覧のS3取得を、利用者ごとに並列にする

`summary=1` は入っている。署名付きURLは作っていない。それでも写真・記録の一覧は15秒を超え、画面が通信を切って再試行している。

遅いのは署名ではない。`getCaptureRecords` が利用者を一人ずつ待ち、そのたびに S3 の `listObjectsV2` を待っている。一覧用の件数をDBに持つ変更はしない。

対象は `scripts/remoteSupportController.js` の `getCaptureRecords`。呼び出しは今のまま。

```http
GET /api/remote-support/capture-records?summary=1&satelliteId=...&startDate=...&endDate=...
```

## 今の動き

利用者の配列を `for` で回し、一人の S3 一覧が終わるまで次の利用者に進まない。日付が一日なら、プレフィックスは利用者あたり1本なので、待ち時間は利用者数のぶん積み上がる。

`summary=1` のレコードの形は変えない。

```json
{
  "date": "2026-11-20",
  "user": { "id": 44, "name": "利用者名", "login_code": "..." },
  "photoCount": 3,
  "screenshotCount": 2,
  "latestAt": "2026-11-20T06:12:00.000Z"
}
```

## 変えること

利用者ごとの S3 一覧を同時に取る。同時実行は 5〜8 人程度で打ち切る。全員を一度に投げない。

同じ利用者の `ContinuationToken` は、今どおり一件ずつ続ける。ページの続きを並列にはしない。

一人が失敗しても、その利用者は飛ばしてログを残し、ほかの利用者の結果は返す。今の `catch` と同じ。

全部そろってから、今どおり日付の新しい順に並べ、`page` と `limit` で切る。`summary=1` のときは `getSignedUrl` を呼ばないままにする。

`summary` が無いときのレスポンスも、利用者を並列にしたうえで、今どおり署名付きURLを付ける。詳細の `GET /api/remote-support/capture-records/:userId/:date` は変えない。

## 確認

同じ拠点・同じ日で、`summary=1` の件数が並列化の前後で一致する。画像URLは含まれない。

画面は15秒でこの通信を切る。利用者の多い拠点で、一覧が15秒以内に返ること。
