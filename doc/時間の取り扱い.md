# 時間の取り扱い

在宅の打刻は、日本時間で入力し、UTC の時計で保存し、表示するときはその瞬間を日本時間に戻す。足したり引いたりしない。

2026-11-19 に本番へ SSH して確認した。ホストの VM は日本時間（`Asia/Tokyo`）。アプリと MySQL は Docker コンテナの中で、どちらも UTC のまま。コンテナには `TZ` が無い。ホストが日本時間でも、中の Node と MySQL は日本時間にならない。

| 場所 | 時刻 |
|---|---|
| ホスト | `Asia/Tokyo`（`timedatectl`）。`/etc/timezone` のファイルだけ `Etc/UTC` |
| `studysphere_backend` | `TZ` 未設定。Node の `offsetMin` は `0` |
| `studysphere_mysql` | `TZ` 未設定。`time_zone` は `SYSTEM`。`NOW()` と `UTC_TIMESTAMP()` は同じ |

## 保存

画面の `HH:MM` は日本時間として扱う。`YYYY-MM-DDTHH:MM:00+09:00` にしてから、UTC の年月日時分秒を MySQL の `DATETIME` 文字列にする。バックエンドはその文字列を、そのまま `remote_support_daily_records` の `mark_start`、`mark_end`、`mark_lunch_start`、`mark_lunch_end` に入れる。

10:00 開始、15:00 終了、休憩 12:00、休憩終了 13:00 なら、保存される時計は `01:00:00`、`06:00:00`、`03:00:00`、`04:00:00`。id 619 と 617 がこの形だった。

## 表示

API は、UTC の Node が `DATETIME` を読んだ瞬間を ISO 文字列で返す。`01:00:00` は `2026-11-19T01:00:00.000Z` になる。表示は、この瞬間の日本時間だけを出す。`src/utils/dateUtils.js` の `formatJapanTimeOfInstant` がそれである。上の例は 10:00、15:00、12:00、13:00 になる。

次の読み方は使わない。

- 返ってきた日本時間の数字を、保存されている UTC の時計だとして、さらに9時間足す。10:00 が 19:00 になる。
- 表示のたびに3時間引く。保存すると、その戻った時刻が書き込まれ、次に開くとさらに3時間戻る。

## 変えてはいけないこと

コンテナを日本時間に変える依頼は、この確認からは出さない。保存も表示も、コンテナが UTC である前提で合っている。ホストのタイムゾーンだけを見て、コンテナも日本時間だと扱わない。
